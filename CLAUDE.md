# Working on this repository

AI-native platform for Belgian real estate agencies. Read README.md for the architecture.

## Rules

- **New behaviour goes in a tool** in `packages/core/src/tools`, registered in `packages/core/src/index.ts`. Pages and server actions call `runTool(tools.x, ctx, input)`; never query the database for domain data directly from `apps/web` (Better Auth session lookups and settings reads in `lib/context.ts` are the exception).
- **Every tool scopes by `ctx.agencyId`.** No exceptions; this is the tenant boundary.
- **Mutating tools call `recordEvent`** with a dotted type such as `appointment.booked`.
- **AI actions that need approval** create a row in `proposals` instead of acting.
- **Times**: store UTC (`timestamptz`); display and compute day boundaries in Europe/Brussels with `@viewing/core/time`.
- **Client components** must not import `@viewing/core` (it pulls in the database). Use `@viewing/core/time` or pass data as props.
- **Schema changes**: edit `packages/db/src/schema`, run `pnpm db:generate --name <change>`, commit the SQL. Auth tables are generated by `npx auth@<better-auth version> generate`.
- **Design**: tokens in `apps/web/app/globals.css`. Near-monochrome, thin borders, status as small coloured dots. Violet (`ai` colour) only for things an AI agent did or proposes. Check light, dark and phone width (390px). On phones: bottom tab bar (`components/mobile-nav.tsx`), card lists instead of tables (`md:hidden` list + `hidden md:table`), no hover-only or drag-only actions.
- **Data residency**: everything in the EU (Vercel `fra1`, Neon `eu-central-1`). New services must offer EU hosting. Exception agreed with the owner: the Claude API (AI triage and drafts) runs outside the EU, disclosed in the privacy notice; any other non-EU processing must be disclosed there too.

## Checks before pushing

`pnpm typecheck`, `DATABASE_URL=… pnpm test` (database tests are skipped without it) and `pnpm --filter @viewing/web build`.

## Booking

- Slots come from `computeSlots` (`packages/core/src/planner/availability.ts`), a pure function with unit tests. Keep it pure.
- Booking and rescheduling take a per-agent advisory lock inside a transaction and re-check the slot; never insert appointments any other way.
- Pages without login (`app/(public)`) resolve the agency through `@viewing/core/public` and then call tools with `publicContext(agencyId)`.
- Staff book for a client (phone, walk-in) at `/appointments/new` through `appointments_book` with `source: "phone"`: email or phone is enough (contacts are matched by email, else by phone digits), `anyTime` takes a time agreed outside the offered slots (agent free with buffer, occupants' windows still apply; staff only), and `confirmToClient` sends the usual confirmation (always, since the agent asked; skipped when there is no email or WhatsApp).
- Open houses (`open_houses`, `tools/open-houses.ts`): one block at a listing with time slots of `slotMinutes` (0 = walk-in, one place for the whole block) holding `perSlot` visitors each; the slots come from the pure `openHouseSlots` and reach every booking path through `viewingSlots` (widget, booking link, planner times, reschedule). The block is busy for the agent everywhere; an `exclusive` one hides the listing's other times until it is over. Visitors are appointments with `openHouseId`: no calendar event each (one for the block), no occupant or agent alert each. One with visitors can't be cancelled; their viewings go first.

## Planner agent and inbox

- The planner lives in `packages/core/src/planner/agent.ts`: triage (category, priority, language, summary), then a draft reply saved as a `proposals` row with `toolName: "conversations_reply"`. Approving runs that tool, optionally with the human's edits.
- Claude is called only through `packages/core/src/ai/client.ts` (`generateStructured`, model `claude-opus-5-5`, server-side refusal fallback). Every AI path has a template or rules fallback, so the product works without `ANTHROPIC_API_KEY`; the UI must say which one produced a draft.
- Offered times always come from the booking engine and are appended by `composeMessage`; the AI never writes times or links itself.
- Outbound messages are stored with `delivery: "simulated"` until Outlook/Gmail/WhatsApp are connected. Never present them as sent.
- Client-facing text exists in NL, FR, EN and DE (`planner/language.ts`, `apps/web/lib/widget-i18n.ts`, `valuation-i18n.ts`, `occupant-i18n.ts`). A client whose language is unknown gets English (`toLang`, `toWidgetLang`).
- When a listing goes under option, sold, rented or off the website, `draftOffMarketNotices` (`planner/off-market.ts`) drafts a message to each client with an upcoming viewing; approving it sends the message and cancels the viewing. Only `active` listings take bookings or get reminders.
- Client actions without a message (booking in the widget, moving or cancelling through the link) go through `noteClientAction`: a system note in the client's preferred channel (WhatsApp if opted in, else email) plus a draft for approval. Routine client messages go out on their own, always as the fixed template (never AI text), unless the agency sets that kind to "Ask me first" (`autonomy.<key> = "suggest"`; `sendsAutomatically` / `proposeAndSend` in `planner/agent.ts`): the confirmation of a booking or move the client made themselves, and new times after they cancel (`booking_confirmations`), reminders (`reminders`), the follow-up after a completed viewing (`follow_ups`), new times after a no-show (`no_shows`), check-ins with quiet leads (`nudges`) and the reply to a portal lead that asks to visit an active listing (`portal_replies`; times and the booking link, `portalAutoReply`). Everything else (replies to questions, AI-written drafts) waits for a human. A visit request for a listing that isn't `active` gets no times or booking link.
- Agents get an email for every viewing or valuation visit a client books, moves or cancels (`planner/agent-alerts.ts`, `emailAgent` in channels: Mailgun from the agency address, else the agent's own connected mailbox). Fixed text; `automations.agentAlerts` turns it off.

## Team and logins

- Logins are Better Auth organization members (`member`, `invitation`); an agent record is tied to its login by `agents.userId`, matched by email on accept (`team_*` tools in `tools/team.ts`). Admins (`owner`/`admin`) invite agents from the agent page (link at `/invite/<id>`, emailed in the agent's language via `emailAgent`, valid 7 days), change roles and remove logins; removing a login keeps the agent and their viewings. Agents (`member`) can't change settings: server actions that change settings start with `requireAdmin()`. "Forgot password" (`/forgot-password`, `/reset-password`) emails a 1-hour link through `team_send_password_reset` (the login's agency via `agencyOfUser`); `team_get_my_agent` gives the menu's "My page" link.

## Client data (GDPR)

- The agency is the controller, we are its processor. `contacts_export` gives everything about a client (download at `/api/contacts/<id>/export`); `contacts_erase` (admins) cancels their upcoming viewings, deletes the contact, leads, conversations, messages, drafts and valuations, empties `events.data`/`automation_runs.detail` that refer to them and keeps past appointments without contact or notes; the `contact.erased` event names no one. New tables with personal data must be handled in `tools/privacy.ts` (export and erase).
- Retention (`automations.retentionMonths`, default 24, 0 = never) runs with the automations: clients without contact for that long are erased, except occupants and leads in `offer`/`won`; unverified valuations go after 30 days.
- Clients see the agency's privacy notice at `/privacy/<agencyId>?lang=` (`lib/privacy-i18n.ts`, NL/FR/EN/DE), linked from the booking and valuation forms and at the end of the first email to a client (`privacyLine` in channels). Update the notice when a new subprocessor or kind of data is added.

## Owners and tenants

- An occupied listing (`access` "owner"/"tenant") only offers slots inside its occupants' windows (`listing_windows`, `listing_blocks`); always pass `listingId` to `availability_slots` when the viewing is for a listing. Occupants act through their token (`occupants_*` tools, `occupantAgency` in `@viewing/core/public`).
- Occupants see visitors only as first name + initial (`visitorLabel`), never contact details. Their alerts (`planner/occupants.ts`) are fixed templates sent automatically unless `autonomy.occupant_alerts = "suggest"`; anything to a visitor stays a draft.

## Channels

- Messages leave the platform only through `sendMessage` (`packages/core/src/channels`); find or create a conversation with `conversationFor`. It stores the message with `delivery` "sent", "failed" or "simulated" and records `message.sent` / `message.failed`. Never insert outbound `messages` rows yourself.
- Email goes from the agent's connected Gmail/Outlook (send-only scopes) or the agency's inbox address via Mailgun EU. Reply-To is the agent's own address plus the inbox address (`automations.repliesToAgent`, on by default): a reply to one of our emails lands in the agent's mailbox and is kept in the app as a silent copy (`copyOnly`: no draft, no unread) so nudges stop; turned off, Reply-To is the inbox address only and replies get drafts. Client emails leave from the agent's own mailbox; the inbox address is only the fallback, and the dashboard lists agents without a working mailbox (`agents_list_without_mailbox`). We never read mailboxes.
- A client message must reach the client somehow: WhatsApp not connected, refused or failed later (status webhook) goes by email once (`fallbackFrom`, `recoveredBy`); an agent mailbox that refuses falls back to Mailgun from the agency address (`mailboxError`). Mailgun bounces (`/api/channels/email/events`, `messages_mark_bounced`) mark the message failed. What still failed shows on the dashboard (`messages_list_undelivered`). Booking/move confirmations (WhatsApp template `booking_confirmed`) and reminders sent by WhatsApp also go by email (`alsoEmail`, copy linked as `emailCopy`/`copyOf`); a later WhatsApp failure then reuses that copy.
- WhatsApp outside the 24-hour window needs a template (`whatsappTemplate`); names and texts are in docs/setup-channels.md.
- The client writes first on WhatsApp: emails to contacts without `whatsappOptIn` end with a wa.me link to the agency's number, prefilled with "(ref XXXXXXXX)" (`channels/whatsapp-invite.ts`, `automations.whatsappInvite`, on by default). The reference routes the message on the shared number and links the sender's number to the contact, turning on `whatsappOptIn`.
- Webhooks (`app/api/channels/*`) verify signatures, resolve the agency through `@viewing/core/inbound`, then call tools with `inboundContext(agencyId, …)`. Inbound handling deduplicates on the provider's message id.
- Portal leads (Immoweb, Zimmo, Immovlan) arrive as forwarded emails, parsed by `channels/portals.ts` (pure, tested), and go through `portal_leads_receive`. Settings → Portal leads (`tools/portal-forwarding.ts`): one-click Outlook inbox rule (`MailboxSettings.ReadWrite`, rules only; a test email from `forwarding-check@` must come back within 15 minutes, else Settings shows it blocked by the Microsoft 365 forwarding policy; organisations that need admin approval get an admin consent link), Gmail confirmation code shown, or (recommended) portals sending straight to us, with the original portal email forwarded to the listing's agent or `channels.leadCopyAddress` (`automations.portalLeadCopies`, on by default; only for mail sent by the portal itself). Non-lead portal mail is ignored.
- Tokens (OAuth, WhatsApp) are encrypted with `CALENDAR_TOKEN_KEY` (`crypto.ts`). Calendar events never invite the client.

## Website widget

- `apps/web/app/widget.js/route.ts` is the embed script agencies put on their site. It resolves the listing by reference (`/api/widget/resolve`) and picks the agent whose name appears first on the page; the booking goes to that agent, else to the listing's responsible agent.
- widget.js reads the site's own look from the page (`readLook`: page background and text colour, body and heading font plus their web font files from same-origin stylesheets, the most common button colour) and passes it to the iframes (`?bg=&fg=&brand=&font=&hfont=&fontsrc=&hfontsrc=`); `components/embed-frame.tsx` and `lib/embed-look.ts` turn it into the widget's tokens (only hex colours, font names and https woff/woff2 files get through; a brand colour set in the back office wins over the detected one; the site's colours win over the visitor's dark mode). Embedded widgets are shown larger (`.embed-large`), the floating panel is 540px wide.
- Booking links (in client messages, "Copy booking link" and the listing's "See on website") point to the listing's page on the agency's own site at `#viewing-booking` when widget.js ran there in the last 30 days (`bookingUrl` in `planner/booking-link.ts`), else to `/book/<id>`. widget.js scrolls to the calendar or opens the floating booking panel for that hash. While the floating booking panel is closed, a card above the button announces the next open house with places left (`openHouse` from `/api/widget/page`, in the page language).
- The same script shows a floating valuation button (bottom right, agency colour, full screen on phones) on every page without a `data-viewing-valuation` placeholder. Agencies switch it in the back office (`settings_update_widget`); `data-launcher="off"` on the script turns it off per page. The script must stay plain ES5 in a shadow root, so agency CSS can't break it.

- Listings come from the agency's own website (`listings_import_website`, daily cron `/api/cron/website`): pages are found and read in `packages/core/src/website` (pure extraction, tested; Claude only when the rules miss key facts, marked "Read by Claude"). Fetches stay on the agency's site and public hosts (`website/fetch.ts`). widget.js reports the page it runs on (`/api/widget/page`): known listing pages get a floating booking button without a placeholder; unknown ones are read in the background.
- The search for listing pages (`website/discover.ts`, resumable over runs, state in `websiteSync.discovery`) walks every overview through all its pages: page links, the site's own GET search form, or tried page addresses; then sitemaps. A new-build overview's projects are read for the units they link below their own address; a project without unit pages is one listing. Each overview stores the count it states next to what we found, and `website_pages.found_on` says which overview showed which page, so the import screen counts per overview and per status. Overviews that fall short are read once more with a browser (`website/browser.ts`: Chromium from `@sparticuz/chromium` on Vercel, `CHROMIUM_PATH` locally, `WEBSITE_BROWSER=off` disables). A listing is identified by its page address, never by its reference: sites reuse references for different properties. `.github/workflows/website-probe.yml` runs the search on the test site (immo-zone.be only; other agencies' sites are not read for testing) and prints stated vs found.

- Widget previews for prospects (`previews_*` tools, `website/preview.ts`, `app/(preview)`): our widget on a prospect's own listings, on a page of ours only (never injected into their site). Their site in a frame when its headers allow it, else the HTML we read shown back from `/preview/site/<token>/<page>` (their own styles, images and scripts load in the visitor's browser; served with `Content-Security-Policy: sandbox`, no origin of ours; links report to the preview instead of navigating), else a page rebuilt from the read data. Keep previews cheap: plain reads within ~15 s, never a browser. Nothing is booked, sent or saved as an agency/listing; the public form needs `PREVIEW_AGENCY_ID`.

## Valuations and recommendations

- The estimate is computed by `packages/core/src/valuation/model.ts` (pure, tested): Statbel municipality median × adjustments, blended with the agency's own sales nearby. AI never produces the amounts.
- Reference data (`market_prices`, `postcodes`) is shared by all agencies and filled by `packages/db/src/import`; see docs/data-import.md.
- The phone must be verified before an estimate is shown. With `WHATSAPP_VERIFY_NUMBER` set, owners send a prefilled code from WhatsApp; without it the code is shown on screen as a demo.
- Comparables are shown by street only, never with house number.
- Recommendations use plain scoring (`planner/similarity.ts`); suggestions to clients are drafts in the inbox like everything else.
